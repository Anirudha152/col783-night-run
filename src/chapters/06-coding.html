Huffman coding

Give short codes to common symbols. Build a tree bottom-up:

  1. List symbols with probabilities.
  2. Merge the two smallest into one node (add probabilities).
  3. Repeat until one node is left.
  4. Label branches 0/1. A symbol's code = path from root to its leaf.

Average length \(= \sum p_i \ell_i = .4(1)+.3(2)+.1(3)+.1(4)+.06(5)+.04(5) = 2.2\) bits. Entropy \(= 2.14\) bits. Very close.

Why Huffman is good, and where it fails

  • Prefix-free / instantaneous: no code is the start of another, so you decode left to right with no lookahead.
  • Uniquely decodable: only one way to split a bit string.
  • Optimal among codes that encode one symbol at a time: \(H \le \bar\ell < H + 1\).

Decode 010100111100 with the tree above: 01010·011·1·1·00 → a3 a1 a2 a2 a6.

Failure case. \(P(a_1) = 0.9, P(a_2) = 0.1\). \(H \approx 0.47\) bits, but every Huffman code word is at least 1 bit, so 1 bit/symbol. Wasteful by 2×.

Fix 1: code pairs of symbols. Probabilities .81, .09, .09, .01 → lengths 1, 2, 3, 3 → \(1.29\) bits per pair = \(0.645\) bits/symbol.

Fix 2: arithmetic coding (next).

Golomb coding: a ready-made code for geometric distributions (small numbers very likely), e.g. run lengths or prediction errors. No tree needed.

Arithmetic coding

Encode the whole message as one number in [0, 1). Each symbol shrinks the current interval in proportion to its probability.

low = 0, high = 1
for each symbol s:
    w = high − low
    high = low + w · cumHigh(s)
    low  = low + w · cumLow(s)
output any number in [low, high)
  • Final width = product of the symbol probabilities. Bits needed \(\approx -\log_2(\text{width})\) = total information. So it approaches the entropy, even for \(p = 0.9\).
  • Not a block code: one code word for the whole message.
  • Practice: reserve an end-of-message symbol (or send the length). Use careful finite-precision rounding. Probabilities can be adaptive or context-based, as long as the decoder updates them the same way.

Quiz 4 Q3, solved: decode 0.15

\(p(a_1) = 0.1\), \(p(a_2) = 0.9\). Message length 3. Code value 0.15. Put \(a_1\) first: \(a_1 \to [0, 0.1)\), \(a_2 \to [0.1, 1)\).

  1. [0 | 0.1 | 1]: 0.15 ≥ 0.1 → a2. New interval [0.1, 1), width 0.9.
  2. Split at 0.1 + 0.1 × 0.9 = 0.19 → [0.1 | 0.19 | 1.0]. 0.15 < 0.19 → a1. New interval [0.1, 0.19), width 0.09.
  3. Split at 0.1 + 0.1 × 0.09 = 0.109 → [0.1 | 0.109 | 0.19]. 0.15 ≥ 0.109 → a2.

Message: a2 a1 a2.

Faster way: rescale. After picking symbol \(s\), set \(v \leftarrow (v - \text{low}_s)/p_s\). 0.15 → a2, \(v = 0.05/0.9 = 0.0556\) → a1, \(v = 0.556\) → a2. Same answer. Still write the intervals: they gave half the marks.

Run-length encoding (RLE)

Store each run of equal pixels as (length, value).

row

runs
  • 8-bit image, 1 byte for length + 1 byte for value.
  • Best case: every run is 256 long → \(C = 256/2 = 128\).
  • Worst case: every pixel differs → each pixel costs 2 bytes → \(C = 1/2\). RLE can expand data.
  • In practice, Huffman-code the run lengths.
  • Binary documents (CCITT fax): run lengths alternate black/white, so no values needed. A 2D version codes the difference from the row above.

LZW: build a dictionary as you go

  1. Start with codes 0–255 for single values.
  2. Find the longest string \(s\) at the current position that is in the dictionary. Output its code.
  3. Add \(s\) + next symbol as a new entry (256, 257, …).
  4. Continue after \(s\).

Input: four rows of 39 39 126 126 (16 pixels, 128 bits).

10 codes × 9 bits = 90 bits. \(C = 128/90 = 1.42\). The decoder rebuilds the same dictionary from the codes, so the dictionary is never sent. Used in GIF, TIFF, PDF.

Symbol-based coding (JBIG2): store a dictionary of glyph bitmaps plus where each appears. Lossy if you ignore small differences; lossless if you also store the difference image.

Answer

a1: [0, 0.1). a2: [0.01, 0.1). Width 0.09, so about \(-\log_2 0.09 \approx 3.5\) → 4 bits (plus 1–2 for safety).

Homework\(P(a) = 15/16\), \(P(b) = 1/16\). Sequences of length 16 with exactly one b. How many bits per sequence with Huffman? With arithmetic coding?
Answer

Huffman with 2 symbols: 1 bit per symbol → 16 bits.

Arithmetic: width \(= (15/16)^{15}(1/16)\). Bits \(\approx 15\times0.093 + 4 \approx 5.4\), so about 6–7 bits. (Ideal for 16 equally likely sequences: 4 bits.)

Build a Huffman code for probabilities 0.5, 0.25, 0.125, 0.125. Compare with entropy.
Answer

Codes 0, 10, 110, 111. Average = 0.5 + 0.5 + 0.375 + 0.375 = 1.75 bits. Entropy = 1.75 bits. Equal, because all probabilities are powers of 1/2.

Cheat sheet · symbol coding

  • Huffman: merge 2 smallest, repeat; code = root→leaf path
  • \(H \le \bar\ell = \sum p_i\ell_i < H+1\); prefix-free
  • Huffman ≥ 1 bit/symbol → bad for \(p=0.9\); fix: blocks
  • Arith. encode: \(w=h-l\); \(h = l + w\,\text{cumHi}\); \(l = l + w\,\text{cumLo}\)
  • Arith. decode: find sub-interval; or \(v\leftarrow(v-\text{lo}_s)/p_s\)
  • Bits ≈ \(-\log_2 \prod p\)
  • RLE 8-bit: best \(C=128\), worst \(C=1/2\)
  • LZW: longest match, output code, add match+next
  • LZW example: 128 bits → 10 × 9 = 90, \(C = 1.42\)
  • JBIG2: glyph dictionary + positions
